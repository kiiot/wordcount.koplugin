## v1.6 — 修「批量统计闪退」（OOM）

**现象**：书架批量统计第 21 本《末日乐园》(3223 页) 时闪退，KOReader 重启。

**根因**（`D:/chrome/crash (3).log` 有铁证）：
```
12:28:12  after retry pages=3223
12:28:12  [memprobe] RSS=150.6 MB peak=150.6 MB
12:28:12  startCount / pageCount=3223
          Killed          ← 内核 OOM Killer，无任何 Lua 报错
          launching...    ← KOReader 重启
```
设备 512MB，crengine 打开这本书已占 150MB，紧接着「一次性取回全文字符串」
（约 7MB Lua 字符串 + crengine 内部副本）把进程顶穿。

**用户明确否决**：不要用「文件大小上限」那条路。

**方案（不用文件大小）**：
1. `mem.lua`（新文件）：读 `/proc/meminfo` 的 MemAvailable 与 `/proc/self/status`
   的 VmRSS/VmHWM。读不到就返回 nil（视为「不知道」，退回保守值，绝不当作充足）。
2. `page_text.lua` 新增 `M.extractRange(doc, p1, p2, page_count)`：取闭区间页文本，
   右开边界用第 p2+1 页的 XPointer（最后一页退到 `DocFragment[N].99999999`）。
   单块上限 `M.BLOCK_MAX_TEXT_BYTES = 3MB`，超了作废退回逐页。
3. `main.lua`：整书路径改为**分块扫描**，块大小由 `chooseBlockPages(job)` 按剩余内存定
   （<45MB→16 页 / <70→48 / <110→120 / 更宽裕→200）。每块扫完 `text = nil` + `collectgarbage("step")`。
4. 内存闸门：每 tick 查 `Mem.critical()`（<28MB）→ 立刻停手，`job.sampled=true` 走外推，
   提示「内存不足：只统计了前 N / M 页，全书约 X 字」。
5. `Mem.beginScan()` 把 GC 调激进（pause 200→130, stepmul 300），`endScan()` 恢复。
6. 每本统计完 `releaseBackgroundDocument()` 后加 `collectgarbage("collect")`。

**删掉的死代码**：`WHOLE_BOOK_MAX_PAGES(5000)`、`WHOLE_BOOK_MAX_BYTES(24MB)`、
`wholeBookCoversAllPages()`、`wholeBookEndsAtBookEnd()`、`compactText()`、
`M.WHOLE_BOOK_CHUNK`。`extractWholeBook` 保留（有测试覆盖、留作文档口径），但主流程不再用。

**踩到的坑**：
- Python 写文件时把 `--` 注释写成了全角 `——`，Lua 直接语法错。批量替换修掉。
- `extractRange` 一开始用 `compareXPointers` 返回值判方向（`cmp ~= -1` 即报错），
  但不同 crengine 版本对 -1/1 的含义不一致；改成**只在 `cmp == 0` 时当空块**，方向不猜。
- 测试 mock 不提供 `compareXPointers`（真机 Document 层未必暴露），逼出上面那条。
- fengari 没有 `io.open`，`mem.lua` 的 readFile 要先判 `type(io) == "table"`。

**验证**：11 个 Lua 文件语法 OK；测试 116 条全绿
（新增 `E:/tmp/wc-test/test_block_scan.lua` 36 条：块内容/拼接=全书/与逐页字数一致/
跨块 in_word/边界/长度闸门/mem 降级）。

**打包**：`E:/agit/wordcount-v1.6.koplugin.zip`（455243 字节，11 文件，正斜杠 + `wordcount.koplugin/` 顶层）。
用 `E:/tmp/wc-test/mkszip.js`（零依赖手写 store 模式 zip）。

**待真机校准**：`mem.lua` 的 `ABORT_AVAIL_MB=28` / `TIGHT_AVAIL_MB=70` 是估的。
新版每次扫描会打 `WordCount: block scan start pages=... block=... avail=..MB rss=..MB peak=..MB`，
拿到日志再调。

## v1.7 — 第三档口径「严格字符数」（对齐平台）

**需求**：字数要和平台后台那个数对齐。前两档（只算文字 / 含标点）本质是
「阅读单位」，不是平台算法：`2019年3月5日` 前两档都是 6，平台是 9。

**做法**：一次扫描同时累计**三种**口径，切口径不重扫。
- `word_count.lua`：`state.count_char` 累加所有「非空白、非控制符」字符；
  `addPage` 返回 6 个值（多出 char 总数与增量）。
- `main.lua`：口径从布尔改成字符串 `plain|punct|chars`；
  `globalPunct()` → `globalMode()`；`punctIncluded(path)` → `countModeOf(path)`；
  `pickCount` → `valueFor(mode, plain, punct, chars, strict)`。
  `job.count_mode` **只在建 job 时解析一次**（旧写法每页都问设置）。
- 缓存：新增 `KEY_COUNT_CHAR = word_count_total_char_v1`；
  全局缓存 `KEY_CACHE` 条目加 `count_char` 字段。
- `source_policy.lua`：每来源规则从三态改四态（plain/punct/chars/nil=跟随）；
  旧布尔值 `true/false` 读取时归一，升级不丢规则。
  预置改为 晋江=chars、起点=plain、番茄=chars。
- `bookshelf_integration.lua`：`setPunctResolver` 现在返回口径字符串；
  新增读 `word_count_total_char_v1`。

**顺手修的真 bug**：`addCustomSource` 占位写的是 `rules[key] = nil`，
等于什么都没存 → 自定义来源加完不出现在菜单。改成写 `"follow"`；
`setRule(@key, nil)` 也不再真删（删了菜单里那条就消失）。

**测试**：`E:/tmp/wc-test/`
- `gen_corpus.py` 生成 12601 字混合语料 + 独立 Python 参照（plain/punct/chars）
- `test_corpus.lua` 31 条：整篇、切三段累加、定点用例，三口径全部逐字一致
- `test_source_policy.lua` 68 条、`test_block_scan.lua` 36 条
- 合计 163 条断言全绿

**已知取舍**：切口径后「已读字数」仍是旧口径算出的 page_units，
只有「全书字数」立刻变；要一致得重新统计一次。
